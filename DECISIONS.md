# Решения и допущения

## Где ТЗ допускало варианты

1. **Роли.** Хранятся в таблице `profiles`. Профиль создаётся автоматически при добавлении пользователя, роль по умолчанию «Исполнитель». Через API в `profiles` нельзя писать вообще, поэтому сменить роль можно только запросом в SQL Editor. Отдельного экрана управления пользователями нет, в ТЗ его не было.

2. **Несколько постановщиков.** Все равноправны: видят все объекты и задачи и могут принять или вернуть любую задачу, а не только созданную ими. В ТЗ сказано «видит всё», ограничение по автору я не вводил.

3. **Исполнитель у задачи обязателен.** Задача без исполнителя не создаётся, назначить можно только пользователя с ролью «Исполнитель» (проверяется в базе). Постановщик не может быть исполнителем.

4. **Редактирование задачи постановщиком.** Название, описание, объект и исполнителя можно менять в любом статусе, кроме «Принята». Принятая задача считается закрытой: её нельзя ни редактировать, ни перевести в другой статус. Удалить задачу можно в любом статусе.

5. **Переназначение.** Разрешено в любом открытом статусе, статус при этом не меняется. Новый исполнитель видит задачу со всей историей, прежний сразу теряет к ней доступ.

6. **Удаление объекта.** Объект с задачами удалить нельзя, база вернёт ошибку, и интерфейс предложит сначала удалить задачи. Так случайное удаление стройки не уносит за собой задачи и историю.

7. **Удаление задачи.** Удаляется вместе со своей историей. Удалять задачи по ТЗ может постановщик, а история без задачи теряет смысл. Если нужна неудаляемая история, задачу лучше переводить в архив, а не удалять (см. «Что не сделано»).

8. **История.** Первая запись создаётся при создании задачи (из пустого статуса в «Новая»), как в первой строке таблицы переходов. Комментарий обязателен только при возврате на доработку, при остальных переходах его можно оставить по желанию. В историю пишутся только смены статуса, правки полей задачи не пишутся (в ТЗ история описана как история статусов).

9. **Переходы строго по таблице.** Постановщик не может сам взять задачу в работу или отправить на проверку за исполнителя. Исполнитель не может принять или вернуть свою задачу. Из «Принята» переходов нет.

10. **Что видит исполнитель.** Свои задачи, объекты, где у него есть хотя бы одна задача (в карточке объекта только его задачи), историю своих задач. Из профилей видит себя и постановщиков. Профили других исполнителей скрыты; если в истории задачи после переназначения есть действия другого исполнителя, вместо имени показывается «Другой сотрудник».

11. **Чужая задача.** Для исполнителя чужая задача выглядит как несуществующая: и при чтении, и при попытке сменить статус ответ «Задача не найдена». Так нельзя даже проверить, существует ли задача.

12. **Как устроена защита.** Несколько слоёв, каждый закрывает обход другого:
    - RLS на всех четырёх таблицах, у роли `anon` нет прав ни на что;
    - права на уровне столбцов: через API можно записать только название, описание, объект и исполнителя задачи (и только постановщику, это решает RLS); статус, автора и дату создания нельзя записать никому;
    - статус меняется только функцией `change_task_status` (security definer), она проверяет роль, исполнителя, переход и комментарий и в той же транзакции пишет историю;
    - триггер на `tasks` дополнительно отклоняет смену статуса в обход функции и правку принятой задачи;
    - в `task_history` права только на чтение; записи создают только триггер при создании задачи и функция смены статуса;
    - служебные функции лежат в схеме `private`, которая не публикуется через API.

13. **Регистрация.** Отключается в настройках Supabase. Даже если её случайно включат, новый пользователь получит роль «Исполнитель» без задач и ничего не увидит.

14. **Статусы в базе** хранятся латиницей (`new`, `in_progress`, `review`, `accepted`, `rework`), русские названия только в интерфейсе.

15. **Хостинг.** Статический сайт с HashRouter (адреса вида `/#/tasks/...`), чтобы работал на GitHub Pages и любом статическом хостинге без настройки сервера.

## Что не сделано

- Управление пользователями и ролями из интерфейса: только через панель Supabase и SQL.
- Журнал правок полей задачи (кто переименовал, кто переназначил): история хранит только статусы.
- Архив вместо удаления задач и объектов.
- Поиск, фильтры по исполнителю, пагинация, вложения (фото со стройки), уведомления, обновление в реальном времени.
- Восстановление пароля.
- Автотесты интерфейса. Проверки безопасности автоматические, но на уровне базы: скрипт `tests/security.test.mjs` на PGlite (PostgreSQL в WebAssembly) с заглушкой схемы `auth`, повторяющей устройство Supabase. На живом проекте Supabase эти сценарии автоматически не прогоняются.
